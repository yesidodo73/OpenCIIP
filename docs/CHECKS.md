# 점검 규칙과 판정

## 가이드 버전 관리

여러 연도의 가이드를 지원할 수 있도록 규칙을 연도별로 분리합니다.

```text
rules/
├── 2025/
└── 2026/
```

각 실행 결과에는 다음 정보를 포함합니다.

- 적용한 가이드 연도
- 점검 항목 코드
- 점검 항목명
- 중요도
- 규칙 버전
- OpenCIIP 버전
- 실행 시각
- 시스템 정보

## 규칙의 근거

각 규칙에는 가이드 내 근거 위치를 기록합니다.

```yaml
reference:
  guide: "2026 주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드"
  section: "Unix 서버 > 계정 관리"
  item: "U-01"
  pages:
    - 12
    - 13
```

근거 페이지는 상세 보기나 보고서에서 확인할 수 있게 합니다.

## 점검 규칙의 역할

점검 규칙은 개발자가 가이드 연도와 OS별 판정 기준을 관리하기 위한 구조입니다.

점검 규칙은 다음을 정의할 수 있습니다.

- 수집 대상
- 실효 설정 확인 방법
- 판정 기준
- 중요도
- 카테고리
- 가이드 근거
- 적용 대상 OS
- 증적 수집 방식

사용자 정의 점검을 지원할 수 있지만, 복잡한 점검을 YAML만으로 억지로 표현하지 않습니다.

YAML 규칙에는 임의 셸 명령이나 복잡한 판정식을 직접 넣지 않습니다. 규칙은 검증된 Go 구현을 가리키는 평가기 식별자와 기준값을 포함하고, 실제 명령 실행, 설정 해석, 판정은 해당 평가기와 플랫폼 구현이 담당합니다.

## 점검 프로필과 플랫폼 계층

점검 항목을 큰 분류로 묶어 선택하거나 재사용하는 구조를 `점검 프로필`이라고 합니다. 자동 조치 결정을 재사용하는 `조치 템플릿`과 혼동하지 않도록 점검 템플릿이라는 명칭은 사용하지 않습니다.

초기 점검 프로필은 다음 가이드 분류를 기준으로 합니다.

- 계정 관리
- 파일 및 디렉터리 관리
- 서비스 관리
- 패치 관리
- 로그 관리

규칙 해석 순서는 다음과 같습니다.

```text
2026 가이드 규칙
→ 점검 프로필
→ Linux 공통 구현
→ RHEL 9 계열 구현
→ Rocky Linux 9.8 예외 및 검증 정보
```

각 계층의 책임은 다음과 같습니다.

- 가이드 규칙: 항목 코드, 명칭, 중요도, 판정 기준, 가이드 근거
- 점검 프로필: 포함할 항목과 실행 순서
- Linux 공통 구현: 실제로 공통인 수집 인터페이스와 자료 구조
- OS 계열 구현: 패키지 관리자, init 시스템, PAM 구조 등 계열별 차이
- 배포판 및 버전 구현: 경로, 명령 출력, 패키지와 서비스 구성 차이 및 검증 정보

RHEL 9 계층은 `family: rhel`과 숫자형 `version_major: "9"`를 함께 요구합니다. 따라서 Rocky, RHEL, AlmaLinux, CentOS 등 같은 계열이라도 8.x나 10.x에는 RHEL 9 매개변수를 적용하지 않습니다. 배포판·마이너 버전 계층은 별도의 정확한 `id`와 `version` 선택자로 더 좁힙니다.

계층 병합 순서와 우선순위는 항상 결정적이어야 합니다. 하위 계층은 명시적으로 허용된 필드만 재정의할 수 있으며, 적용한 최종 규칙과 재정의 출처를 결과와 증적에서 확인할 수 있어야 합니다.

배포판 지원 상태는 규칙별 `verification`과 분리된 바인딩 계층의 `platform_verification`으로 선언합니다. 이 필드는 정확한 배포판 `id`와 전체 `version`을 함께 지정하고 `version_major`를 사용하지 않는 계층에서만 허용합니다. 따라서 Linux 공통이나 RHEL 9 계열처럼 넓은 선택자가 특정 배포판의 검증 완료를 대신할 수 없습니다.

플랫폼 탐지기는 `/etc/os-release` 등에서 사실만 수집하고 특정 배포판의 지원 상태를 코드에 내장하지 않습니다. 규칙 번들은 일치하는 계층을 `priority` 오름차순과 계층 `id` 순서로 결정적으로 적용하며, 마지막으로 일치한 `platform_verification`을 `PlatformInfo.Support`에 반영합니다. `pending`은 `targeted`와 검증 대기 경고, `verified`는 `verified`와 빈 경고, `rejected`는 `unsupported`와 제외 경고가 됩니다. 정확히 일치하는 선언이 없으면 `unsupported`와 검증 정보 부재 경고를 사용합니다.

아키텍처 선택자가 없는 플랫폼 검증 선언은 해당 배포판·버전에서 일치하는 모든 아키텍처에 적용됩니다. 이런 선언은 지원하려는 모든 아키텍처의 증적을 확보한 뒤에만 `verified`로 전환하고, 일부 아키텍처만 검증했으면 `architecture`를 포함한 더 좁은 계층을 사용합니다. 플랫폼이 `verified`여도 개별 규칙의 검증 상태는 별도이며 자동 조치는 플랫폼·규칙·조치 정의가 모두 검증된 경우에만 허용합니다.

최초 검증 대상은 Rocky Linux 9.8입니다. 다른 Linux 배포판이나 버전은 플랫폼 구현이 일부 호환되더라도 실제 검증 전에는 지원 대상으로 표시하지 않습니다. 필요한 플랫폼 바인딩이 없거나 적용 가능성이 불명확하면 `UNKNOWN`의 `unsupported_configuration`으로 판정합니다.

플랫폼 바인딩으로 해석된 개별 규칙의 `verification`이 `pending`이면 읽기 전용 수집과 예비 판정까지 수행할 수 있지만, 예비 `PASS`, `FAIL`, `NOT_APPLICABLE`을 최종 상태로 노출하지 않습니다. 결과에는 예비 상태와 확인값을 남기고 최종 상태는 `UNKNOWN(unsupported_configuration)`으로 제한합니다. 수집·파싱 자체가 실패하면 검증 대기 여부와 관계없이 `ERROR`입니다. 실제 Rocky Linux 9.8 VM 증적을 통과한 항목만 `verified`로 전환합니다.

## 판정 상태

```text
PASS
FAIL
UNKNOWN
NOT_APPLICABLE
ERROR
SKIPPED
```

- `PASS`: 가이드 기준 충족
- `FAIL`: 가이드 기준 미충족
- `UNKNOWN`: 자동 확정 불가 또는 수동 확인 필요
- `NOT_APPLICABLE`: 해당 서비스나 기능을 사용하지 않음
- `ERROR`: 권한, 명령 실패, 파싱 실패 등으로 점검하지 못함
- `SKIPPED`: 사용자 설정에 따라 제외됨

필요하면 `UNKNOWN`의 원인을 내부 필드로 구분합니다.

```text
insufficient_evidence
manual_verification_required
unsupported_configuration
ambiguous_result
```

## 판정 기준

판정은 가이드 기준을 우선합니다.

가이드 기준과 OS 기본값 또는 다른 보안 권고가 충돌하면:

- 판정은 가이드 기준으로 수행
- OS 기본값이나 실무상 차이는 참고 정보로 표시
- 자동 조치 전에 영향과 충돌 가능성을 표시

## 실효 설정값

우선순위는 다음과 같습니다.

1. 실제 적용된 설정값
2. 설정 파일 전체 해석
3. 설정 파일 일부 파싱
4. 단순 문자열 검색

실효 설정 확인 명령이 있더라도 해당 명령의 신뢰성과 실행 영향을 검토합니다.

## 배포판별 차이

배포판별 차이는 반드시 별도 처리합니다.

특정 배포판에서만 검증한 구현을 모든 Linux에 공통 적용하지 않습니다.

너무 오래된 레거시 환경까지 무조건 지원한다고 가정하지 않습니다. 구조는 확장 가능하게 유지하고, 실제 지원 여부는 검증된 환경만 기준으로 합니다.
