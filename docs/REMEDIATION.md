# 자동 조치

## 기본 원칙

자동 조치는 별도 옵션으로만 활성화합니다.

현재 조치 템플릿은 구현되어 있지 않으므로 모든 조치 계획에서 사용자 승인을 받아야 합니다. CLI와 TUI는 plan digest를 표시한 뒤 별도 승인을 요구하며, 승인을 적용 명령으로 간주하지 않습니다.

승인 전에 다음 정보를 보여줍니다.

- 현재 설정
- 변경 예정 설정
- 변경 대상 파일 또는 서비스
- dry-run 결과
- 예상 영향
- 위험 수준
- 백업 위치
- 롤백 가능 여부

사용자가 진행을 승인한 뒤에만 실제 변경을 수행합니다.

## 현재 구현 범위

`openciip remediate`와 TUI의 조치 화면은 안전 계약 검토를 위한 실험적 인터페이스입니다. 현재 Rocky Linux 9.8 플랫폼 바인딩, U-01~U-67의 실효 규칙 바인딩, 세 개의 내장 조치 정의는 모두 `pending`이므로 플랫폼·규칙·조치 정의 검증 gate에서 계획이 거부됩니다. 적용은 계획을 만든 것과 동일한 실행 파일 identity를 다시 확인하며 `dev`, `unknown`, 수정된 빌드를 거부합니다. 사용자 요청 롤백도 정식·수정되지 않은 빌드만 허용하되, 수정 릴리스로 복구할 수 있도록 원본 실행 파일 digest 완전 일치 대신 journal schema·작업 처리기·호스트·백업·현재 자원 상태를 검증합니다. 검증 완료 릴리스와 실제 VM 증적이 마련되기 전에는 운영 지원 기능으로 표시하지 않습니다.

현재 내장 조치 정의는 기존 일반 파일에서 허용되지 않은 소유자 UID를 안전한 소유자로 바꾸고 mode의 금지 비트만 제거하는 `file_metadata` 작업을 지원합니다. 조치 가능한 파일에서는 허용된 소유자, 더 엄격한 mode, GID, 내용, inode, 부모 디렉터리, 링크와 SELinux context를 보존합니다. POSIX ACL 또는 SELinux context 이외의 확장 속성이 있는 파일은 검증된 복원 구현이 없으므로 계획 전에 거부합니다. 파일 내용·생성·삭제, 서비스 상태와 systemd 작업은 현재 지원하지 않습니다.

레시피는 자동 조치 범위를 넓히지 않도록 정확한 배포판 `id`와 `version`을 반드시 지정하며 `version_major` 범위 선택은 허용하지 않습니다. 모든 레시피는 별도의 `verification` 메타데이터를 가져야 합니다. 상태는 `pending`, `verified`, `rejected` 중 하나이며, `verified`는 중복되지 않는 정규화된 검증 환경, RFC 3339 `verified_at`, 하나 이상의 중복되지 않는 소문자 SHA-256 `evidence_sha256`을 모두 요구합니다. `pending`과 `rejected`에는 검증 완료 시각이나 증적 digest를 기록할 수 없고 계획 gate를 통과하지 못합니다. 이 메타데이터도 조치 정의 digest에 포함됩니다. 각 작업은 `allowed_owners`, `remediation_owner`, `maximum_mode`를 선언합니다. 계정 이름은 계획·승인·적용 시점의 NSS UID로 다시 해석하고, 현재 UID가 허용 집합에 있으면 유지합니다. 허용되지 않은 경우에만 `remediation_owner`로 바꾸며 목표 mode는 `current_mode & maximum_mode`로 계산하여 기존보다 권한을 넓히지 않습니다. GID는 현재 값을 그대로 사용합니다. 검증된 롤백은 순방향 적용과 권한이 다릅니다. 순방향 적용은 기존에 없던 권한 비트를 추가할 수 없지만, 롤백은 영속화된 범위·정확한 백업 digest·현재 after 또는 허용된 부분 상태·자원 identity를 모두 증명한 경우에만 백업된 원래 권한 비트를 복원할 수 있습니다.

조치 상태의 기본 경로는 `/var/lib/openciip/remediation`입니다. 상태 조회는 읽기 전용으로 WAL을 검사하고, 계획·승인·취소·적용·롤백·복구는 호스트 전체 조치 잠금을 획득합니다.

dry-run은 백업 예정 namespace를 `<stateRoot>/<runID>/backups/<changeSet>/<generated-artifact>/{content,metadata.json}` 형식으로 표시합니다. `generated-artifact` 이름은 적용 직전 배타적으로 백업을 만들 때 무작위로 확정되므로 계획 단계에서는 특정 이름을 약속하지 않습니다. 생성된 실제 상대 경로와 digest는 저널에 기록합니다. 계획에는 항목별 롤백과 실행 전체 롤백 가능 여부도 함께 표시하고 plan digest에 포함합니다.

## 조치 절차

1. 완료된 비공개 보고서의 소유권·권한과 현재 호스트·플랫폼·규칙 identity 확인
2. 대상 점검 evaluator 재실행과 `FAIL` 재확인
3. 현재 자원 상태와 적용 가능성 확인
4. 변경 예정 내용 생성
5. dry-run, 영향도와 위험 수준 표시
6. plan digest를 포함한 사용자 승인 확인
7. 변경 직전 현재 상태 재확인
8. 변경 대상 백업과 무결성·영속성 확인
9. write-ahead apply intent 영속화
10. 실제 변경과 같은 자원 handle에서의 동기화·후행 상태 수집
11. 같은 전역 조치 잠금을 유지한 채 해당 변경 세트의 자원 후행 상태와 원래 점검 evaluator의 `PASS` 검증
12. evaluator까지 성공한 변경 세트와 작업을 하나의 revision에서 `verified`로 영속화
13. 모든 항목 적용 뒤 공유 자원의 마지막 작성자 상태와 전체 대상 evaluator를 다시 검증
14. 실패 시 승인된 `rollback_item` 또는 `rollback_run` 정책에 따른 롤백
15. 조치 결과와 미해결 상태 보고

dry-run 결과를 보여주기 전에 실제 변경을 수행하지 않습니다.

## 조치 등급

```text
SAFE
CAUTION
DANGEROUS
UNSUPPORTED
```

등급과 관계없이 템플릿이 없으면 사용자 승인을 받아야 합니다.

## 자동 조치 가능 조건

자동 조치는 `FAIL` 중에서도 다음 조건을 만족한 항목만 대상으로 합니다.

- 조치 방법이 가이드 근거를 가짐
- 대상 플랫폼, 점검 규칙과 조치 정의가 각각 `verified`이고 조치 정의에 실제 VM 증적 digest가 기록됨
- 변경 전 상태를 복원할 수 있음
- 문법 및 적용 검증 방법이 있음
- 서비스 영향 확인 방법이 있음

`UNKNOWN`, `ERROR`, `SKIPPED`는 자동 조치하지 않습니다.

## 백업과 롤백

- 변경 전 백업은 필수입니다.
- 백업 실패 시 조치를 중단합니다.
- 변경 후 검증 실패 시 자동 롤백을 시도합니다.
- 롤백 실패 시 사용자에게 즉시 알립니다.
- 원본 파일의 소유자, 그룹, 권한을 복원할 수 있어야 합니다.
- 백업 파일 위치, 보호 상태와 무결성 정보를 조치 저널에 남깁니다.

`file_metadata` 적용과 복원은 승인한 일반 파일을 심볼릭 링크를 따르지 않고 열어 같은 file descriptor에서 소유권, 권한, 동기화와 후행 상태 수집을 수행합니다. 경로가 다른 inode로 바뀌거나 내용·부모·링크·확장 속성·SELinux identity가 달라지면 자동으로 덮어쓰지 않고 복구 필요 상태로 남깁니다.

부작용이 시작된 뒤 요청 context가 취소되더라도 저널 기록, 후행 상태 수집과 필요한 롤백에는 취소 신호를 분리한 새로운 제한 시간 context를 단계별로 사용합니다. 무제한 background context로 영구 대기하지 않으며, 영속화 결과가 불명확하면 최신 WAL을 다시 읽어 이미 커밋된 revision인지 확인합니다.

### 변경 세트와 실행 저널

각 점검 항목의 조치는 하나의 변경 세트로 관리합니다. 변경 세트가 여러 파일이나 서비스를 다루면 일부만 변경된 상태가 남지 않도록 하나의 논리적 트랜잭션으로 취급합니다.

실제 변경 전에 실행 저널에 다음 정보를 기록합니다.

- 실행 식별자와 항목 코드
- 적용 순서
- 변경 대상 파일과 서비스
- 변경 전 상태와 백업 위치
- 파일 유형, 소유자, 그룹, 권한
- 변경 전후 무결성 확인값
- dry-run과 사용자 승인 정보
- 적용, 검증, 롤백 결과

저널과 백업 기록이 안전하게 저장되지 않으면 실제 변경을 시작하지 않습니다. 중단되거나 비정상 종료된 실행도 저널을 사용해 복구 가능 상태를 판단할 수 있어야 합니다.

apply intent 뒤 대상이 변경 전 상태와 정확히 같음이 확인되면 그 관측값을 무효과 증적으로 기록하고 실패 실행으로 종결합니다. 실제 복원이 없었으므로 이 작업을 롤백 대상으로 노출하거나 성공 롤백으로 기록하지 않습니다. 기존 rollback intent가 있을 때만 같은 변경 전 관측을 중단된 롤백의 완료로 판정합니다.

복구 중 현재 상태를 중단된 순방향 적용의 `Desired` 또는 원자적 부분 metadata 상태로 추론하는 것은 아직 `AppliedAt`, `ObservedAfter`, rollback intent가 없는 `state_inferable` 작업에만 허용합니다. 이전 적용 완료나 후행 관측 이력이 있으면 현재 값이 목표 범위 안에 있더라도 새 외부 변경 가능성을 배제할 수 없으므로 `recovery_required`를 유지합니다.

### 롤백 범위

엔진과 CLI 계약은 다음 두 롤백 범위를 모두 구현합니다. 다만 현재 `pending` gate로 운영 적용과 실제 VM end-to-end 롤백은 아직 실행할 수 없습니다.

- 항목별 롤백: 선택한 점검 항목의 변경 세트만 되돌림
- 실행 전체 롤백: 해당 조치 실행에서 적용된 모든 변경 세트를 역순으로 되돌림

항목별 롤백은 해당 항목 이후에 같은 파일이나 서비스가 다른 항목에서 변경되지 않은 경우에만 독립적으로 수행합니다.

여러 항목이 같은 파일이나 서비스에 영향을 주면 공유 자원 충돌로 기록합니다. 공유 자원을 수정하는 항목은 하나의 롤백 그룹으로 묶거나, 선행 항목을 되돌릴 때 의존하는 후속 항목까지 함께 되돌립니다. 후속 변경을 덮어쓸 가능성이 있는 단독 롤백은 수행하지 않습니다.

같은 자원의 작성자 A, B를 역순으로 복원할 때 이미 복원된 B의 `ObservedRollback`을 A의 영속 `ObservedAfter`와 연결해 writer chain을 검증합니다. 중단된 A의 부분 metadata 상태는 A의 rollback intent가 중단 전에 WAL에 영속화된 경우에만 재개하며, intent가 없는 부분 상태는 외부 변경으로 취급합니다.

실행 전체 롤백은 적용의 역순으로 수행합니다. 일부 자원의 롤백이 실패하면 즉시 사용자에게 알리고 실패 원인을 기록합니다. 실패한 자원과 독립적인 나머지 자원은 복원을 계속 시도하되, 실패한 후행 writer의 상태에 의존하여 안전하게 복원할 수 없는 선행 변경은 중단합니다. 완료 후 전체 성공, 부분 성공, 실패 상태를 명확히 보고합니다.

사용자 요청 롤백은 실행 전에 현재 저널 revision의 범위와 순서를 미리 보여줍니다. 항목별·실행 전체 롤백 모두 미리보기 digest를 다시 계산해 승인한 값과 비교하며, revision이나 cascade 범위가 바뀌면 변경 없이 새 미리보기를 요구합니다.

정상 종료 상태인 `completed`, `rolled_back`, `completed_with_rollbacks`, `canceled`, `failed`에는 `UnresolvedChangeSets`, 중간 변경 세트 상태, intent 상태 또는 미완료 롤백 시도를 남길 수 없습니다. 항목 롤백 밖에 남는 변경은 모두 `verified`인 안정 상태일 때만 `completed_with_rollbacks`로 종료하며, 적용·검증·롤백 중간 상태가 남으면 `recovery_required`가 우선합니다.

항목 정책에서 현재 항목이 첫 부작용 전에 실패하면 실제 롤백 시도를 만들지 않습니다. 앞서 검증된 변경은 안정된 적용 상태로 보존하되 전체 실행은 `failed`로 기록합니다. `completed_with_rollbacks`와 성공한 rollback attempt는 하나 이상의 실제 대상이 승인된 범위에서 복원된 경우에만 사용합니다.

### 비정상 종료 복구

`recover`는 마지막 유효 WAL, 백업과 현재 자원 상태를 비교해 작업을 적용됨, 롤백됨, 미적용 또는 모호함으로 정합화합니다. 이 명령 자체는 대상 파일을 새로 변경하지 않습니다. 확인된 적용분이 남으면 복구 결과를 확인한 뒤 새 `rollback preview item|run`과 새 digest로 다시 승인해야 합니다.

중단된 롤백 attempt는 현재 상태를 정합화한 뒤 기존 attempt 자체를 `succeeded`, `partially_succeeded` 또는 `failed`로 닫습니다. 복원할 작업이 남으면 이를 몰래 재개하지 않고 retry 가능한 실패·부분 상태로 남겨 새 미리보기와 승인을 요구합니다. 이미 완료된 실패·부분 attempt나 별도 attempt 표식 없이 복원이 정확히 끝난 운영자 조치 상태를 사후 확정할 때는 새 `crash_recovery` attempt로 감사 기록하고 실행 상태를 종결합니다.

### 적용 전 계획 취소

`planned` 또는 `approved` 상태이고 적용 준비나 부작용이 전혀 시작되지 않은 실행만 취소할 수 있습니다. 취소는 먼저 `canceling` 의도를 저널에 영속화하고 `payloads/<runID>`의 미사용 desired payload만 삭제합니다. 저널과 백업 경로는 삭제하지 않습니다. 삭제 실패는 `cancel_failed`로 기록하고 재시도할 수 있어야 하며 성공으로 축소하지 않습니다.

## 향후 조치 템플릿 계약

조치 템플릿을 추가할 경우 사용자가 여러 서버에서 같은 선택을 재사용하기 위한 사용자 설정으로만 사용합니다. 현재 CLI와 TUI에는 템플릿 생성·승인·적용 기능이 없습니다.

최소 포함 항목:

- 가이드 연도
- 대상 OS 계열
- 대상 OS 버전 범위
- 항목별 진행 여부
- 사용자 선택값
- 적용 제외 항목
- 생성 시각
- 템플릿 버전

다른 서버에 적용하기 전에 호환성을 확인합니다.

OS, 버전, 서비스 구성, 설정 경로가 다르면 그대로 적용하지 않습니다.

점검 및 조치가 완료된 뒤, 사용자가 선택한 조치 결정을 템플릿으로 저장할지 물을 수 있습니다.

## 점검 규칙과의 분리

점검 규칙은 개발자가 가이드별 판정 기준을 관리하기 위한 구조입니다.

조치 템플릿은 사용자가 조치 결정을 재사용하기 위한 구조입니다.

두 구조를 혼합하지 않습니다.
